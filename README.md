### 3

#### Вариант 1. Централизованное хранение логов на сетевом ресурсе
````
Как работает: приложения пишут логи в файлы, скрипт копирует их на общий сетевой диск или файловый сервер.

Реализация:
Настройте приложения на запись ошибок в отдельные файлы (например, app-errors.log).
Создайте сетевой ресурс (NAS, SMB‑шару, облачное хранилище типа Яндекс Диска/Google Drive).
На каждом сервере настройте регулярное копирование логов (через cron в Linux или Task Scheduler в Windows).

Плюсы:
минимум настроек;
не требует дополнительного ПО;
быстрый старт.

Минусы:
нет поиска и фильтрации;
задержки при копировании;
сложно отслеживать логи в реальном времени.
````

#### Вариант 2. Использование встроенных механизмов ОС
````
Linux:
настройте сбор ошибок через syslog (rsyslog или journald);
разработчики могут просматривать логи через journalctl или tail -f.

Windows:
используйте Windows Event Log;
настройте пересылку событий на центральный сервер через Event Log Forwarding;
просматривайте логи через Event Viewer или PowerShell (Get-WinEvent).

Плюсы:
встроенная функциональность ОС;
минимальная нагрузка на систему;
поддержка из коробки.

Минусы:
ограниченная фильтрация;
сложности с парсингом структурированных логов (JSON и т. д.).
````

#### Вариант 3. Лёгковесные open‑source‑решения
````
Fluentd + Elasticsearch + Kibana (урезанный ELK):
установите Fluentd на каждый сервер — он собирает логи и отправляет их;
разверните Elasticsearch на одном сервере (можно в минимальной конфигурации);
используйте Kibana для визуализации (базовые функции бесплатны).


Альтернативы:
Graylog — проще в настройке, чем полный ELK;
Loki + Grafana — легковесный вариант для логов, хорошо интегрируется с существующим мониторингом.

Плюсы:
поиск и фильтрация по ключевым словам;
дашборды и графики;
оповещения о критических ошибках.

Минусы:
требуется минимальная настройка;
Elasticsearch может потреблять много памяти.
````

#### Вариант 4. Отправка логов в мессенджеры или почту
````
Как работает: скрипт мониторит файлы логов, при обнаружении ошибок отправляет уведомления.

Реализация:
для Telegram: используйте бота и curl для отправки сообщений;
для Slack: настройте incoming webhook;
для почты: скрипт на Python/PowerShell с отправкой через SMTP.

Плюсы:
мгновенные уведомления;
доступ с телефона;
простота настройки.

Минусы:
шум при частых ошибках;
нет архивации логов.
````

#### Вариант 5. Использование облачных бесплатных тарифов
````
Сервисы с бесплатными планами:
Sentry — для отслеживания ошибок в коде (особенно хорошо для веб‑приложений);
Loggly — бесплатный тариф на 200 MB/день;
Papertrail — 100 MB/день бесплатно.

Плюсы:
готовые дашборды;
поиск и оповещения;
не нужно поддерживать инфраструктуру.

Минусы:
ограничения по объёму;
данные уходят в облако.
````

#### Вариант 6. Упрощённый сбор через текстовые файлы и Git
````
Как работает: логи записываются в файл, который периодически коммитится в Git‑репозиторий.

Реализация:
Приложения пишут ошибки в errors.log.
Скрипт раз в час делает git add, git commit и git push в репозиторий.
Разработчики клонируют репозиторий и ищут ошибки через grep.

Плюсы:
история изменений логов;
простой поиск через Git;
бесплатно.

Минусы:
задержки в обновлении логов;
не подходит для высоконагруженных систем.

Безопасность. При открытии доступа к логам убедитесь, что в них нет чувствительных данных (пароли, токены).
````

### 5

#### Pull‑система (Pull Model)
````
Принцип работы: сервер мониторинга периодически опрашивает (pull) агенты или сервисы на предмет метрик. Пример — Prometheus.

Плюсы
  Контроль над источниками данных. Сервер опрашивает только те агенты, которые явно настроены в системе мониторинга — исключаются «неожиданные» источники.
  Упрощённая отладка. Поскольку данные запрашиваются по HTTP(S), их можно получить вручную через браузер или curl для проверки.
  Безопасность. Легко настроить единый прокси‑сервер с TLS для безопасного взаимодействия между системой мониторинга и агентами, даже если они разнесены по разным сетям.
  Простота развёртывания агентов. Агенту не нужно знать о системе мониторинга — достаточно предоставить endpoint с метриками (например, /metrics).
  Масштабирование сервера мониторинга. Нагрузка предсказуема: частота опросов задаётся централизованно.
  Интеграция с service discovery. Хорошо работает с механизмами автоматического обнаружения сервисов (Kubernetes, Consul).

Минусы
  Проблемы с короткоживущими сервисами. Если контейнер или функция (FaaS) живёт меньше интервала опроса, метрики могут быть потеряны.
  Нагрузка на цели при опросе. Массовый опрос сотен/тысяч целей может создавать всплески нагрузки на целевые системы.
  Ограниченная частота сбора. Высокая частота опросов (например, каждую секунду) создаёт значительную сетевую нагрузку.
  Неравномерность данных. При большом количестве целей время сбора метрик растягивается — данные могут быть не совсем синхронными.
  Необходимость service discovery. Требуется дополнительная инфраструктура для отслеживания динамически изменяющегося набора целей.
````

#### Push‑система (Push Model)
````
Принцип работы: агенты самостоятельно отправляют (push) метрики на сервер мониторинга. Примеры — Graphite, TICK.

Плюсы
  Поддержка короткоживущих сервисов. Даже если контейнер прожил недолго, он успевает отправить метрики перед завершением.
  Низкая задержка. Данные поступают почти в реальном времени — агент отправляет метрику сразу после измерения.
  Гибкость настройки. Каждый агент может индивидуально настраивать частоту отправки и набор метрик.
  Репликация данных. Легко отправлять одни и те же метрики в несколько систем мониторинга или резервных копий.
  Меньшая нагрузка на цели. Целевая система не выполняет опрос — она просто отправляет данные по мере готовности.
  Работа через NAT/firewall. Агенты за сетевыми ограничениями могут инициировать соединение наружу, тогда как pull‑модель требует доступности целей извне.

Минусы
  Отсутствие гарантии доставки. При использовании UDP (часто для производительности) пакеты могут теряться без уведомления.
  Перегрузка приёмника. Сервер мониторинга может быть завален данными, если агенты отправляют метрики слишком часто.
  Сложность настройки агентов. Каждому агенту нужно явно указать endpoint сервера мониторинга и параметры отправки.
  Проблемы с безопасностью. Сложно централизованно контролировать, какие агенты отправляют данные — возможны подделки.
  Дублирование данных. При сбоях в сети агент может отправить одну и ту же метрику несколько раз.
  Сложности с логированием. Сбор логов в push‑модели требует дополнительных механизмов буферизации и повторных попыток отправки.
````


### 6
````
  Из перечисленных систем к pull-модели относятся:
  Prometheus. По умолчанию Prometheus использует pull-модель: сервер периодически опрашивает (скрапит) целевые системы через HTTP-endpoints, запрашивая метрики. Это основная модель работы системы. 
  Zabbix (в пассивном режиме). По умолчанию Zabbix работает в pull-модели: сервер подключается к агентам на мониторящихся машинах, запрашивает данные, и агенты возвращают значения. 

  К push-модели относятся:
  Nagios. Nagios использует push-модель, основанную на плагинах. Агенты (плагины) устанавливаются на мониторящиеся системы и активно отправляют данные на сервер Nagios.
  TICK (Telegraf, InfluxDB, Chronograf, Kapacitor) можно отнести к push-модели. Telegraf, как агент сбора данных, активно отправляет метрики в InfluxDB. 
  Zabbix (в активном режиме). В активном режиме Zabbix-агент самостоятельно подключается к серверу или прокси, запрашивает список активных элементов, выполняет их локально и периодически отправляет результаты обратно. 

  VictoriaMetrics является гибридной системой. Она поддерживает как pull-, так и push-модели сбора метрик. По умолчанию для новых сервисов в VictoriaMetrics используется push-модель, но можно выбрать pull-модель при  настройке. Данные можно как «толкать» на сервер, так и «тянуть» с помощью сервера. 
````
